Problem and user

The sim-to-real gap is tuned by hand

Robotics and physical-AI teams train in simulation, then lose performance on real hardware because the simulator doesn't match reality. Matching a sim to a real scene today means measuring objects and adjusting friction, mass and restitution until the replay looks right. It takes hours per scene and nobody checks it rigorously.

User: a robotics engineer who needs a MuJoCo scene of a real tabletop setup whose simulated dynamics match what actually happens.

How it works

Six steps from phone footage to a calibrated scene

  1. Film

    A fixed camera records a tabletop event: dominoes toppling or a tower falling. A sheet of US-letter paper sets the scale.

  2. Perceive

    Argon watches the video and returns a scene graph (objects, sizes, poses, camera) and a timestamped timeline of real events.

  3. Compile

    The scene graph compiles to MJCF with deterministic code and runs in MuJoCo.

  4. Watch and critique

    The sim renders from the estimated camera, sits side by side with reality, and Argon explains every mismatch.

  5. Fix

    Argon edits the scene graph. The loop repeats until sim and reality agree.

  6. Predict

    "What if I remove domino 4?" The calibrated sim predicts the outcome, then a real take scores the prediction.

Illustration of the target behavior, not measured data. Round 0 runs too fast (friction too low); by round 4 the sim timeline lines up with reality.

Data model

The scene graph is what Argon edits

Units are meters, kilograms and seconds. The origin is the center of the paper, +x runs along its long edge, +z points up.

{
  "camera":  { "pos": [x, y, z], "lookat": [x, y, z], "fovy": 45 },
  "table":   { "friction": 0.6 },
  "objects": [
    { "name": "d1", "kind": "box", "size": [0.024, 0.008, 0.048],
      "pos": [x, y, z], "yaw_deg": 0, "mass": 0.01,
      "friction": 0.4, "restitution": 0.1 }
  ],
  "pushes":  [ { "object": "d1", "t": 0.0, "impulse": [0.002, 0, 0] } ]
}

// Event, produced by Argon (real) and by the simulator (sim)
{ "t": 1.42, "kind": "contact" | "fallen" | "rest", "a": "d3", "b": "d4" }
Metrics

Scored on event timing, aligned to the first contact

  • Timing error: mean |tsim − treal| over matched events, in ms. The headline number.
  • Event recall: share of real events matched in sim (same kind and objects, within 0.5 s).
  • Parameter error (F11): relative error of recovered size, pose, friction and mass against ground truth.
  • Prediction error (F8): timing error and recall of the predicted timeline against the real intervention take.
Stack

Python, MuJoCo and the Interactions API

  • Python 3.11 with uv. Packages: google-genai, mujoco, opencv-python, numpy; system ffmpeg for compositing.
  • Models come from GEMINI_MODEL and the optional GEMINI_FAST_MODEL. No model IDs in code.
  • Each round writes scene.json, scene.xml, sim.mp4, side_by_side.mp4, events.json, metrics.json and critique.md.

Out of scope
  • Deformables and fluids
  • Moving or multiple cameras
  • Articulated objects
  • Photoreal rendering
Risks
  • Poor camera pose: paper reference plus a static-layout phase before dynamics.
  • Video cost and latency: clips of 10 s or less, downscaled; history benefits from implicit caching.
  • Venue Wi-Fi blocks phone transfer: capture on the laptop webcam.
  • API shape differs from docs: a thin wrapper checked against the installed SDK.
